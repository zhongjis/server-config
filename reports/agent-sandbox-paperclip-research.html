Executive recommendation

Do not deploy sandbox-cr straight to production. Start with a Phase 1 job backend smoke test only, then move to Phase 2 sandbox-cr after API-version compatibility and security gates pass.

Reason: Agent Sandbox is still moving fast, Paperclip's Kubernetes plugin is alpha, and the current sandbox-CR path appears coupled to older Agent Sandbox API expectations.

Agent Sandbox: what it adds

Agent Sandbox is a Kubernetes SIG Apps CRD/controller project for agent execution environments. The core concepts are Sandbox, SandboxTemplate, SandboxClaim, and SandboxWarmPool [1][3][4][5].

Sandbox

Defines an isolated runtime unit backed by Kubernetes primitives, with API fields for container-like execution surfaces [3].

SandboxTemplate

Provides reusable environment templates, so agents can claim pre-defined runtime shapes instead of rebuilding pod spec details each time [4].

SandboxClaim

Lets consumers request a sandbox from a template or pool, separating request flow from runtime provisioning [5].

SandboxWarmPool

Keeps pre-warmed sandboxes available for lower startup latency [5].

Release posture

  • Installation should use exact release artifacts: manifest.yaml for core CRDs/controller, plus extensions.yaml when templates, claims, and warm pools are needed [2].
  • Current v0.5.0rc1 is a pre-release and moves the API to v1beta1 with no migration path noted in the release stream [6].
  • v0.4.6 stable exists, but the Paperclip plugin compatibility surface must be checked before choosing it [6].

Gate before Phase 2: confirm whether Paperclip's sandbox-cr backend targets Agent Sandbox v1alpha1 or v1beta1. A CRD API mismatch will fail reconciliation or create invalid runtime objects.

k3s fit and constraints

The homelab can run the early smoke path, but stronger sandbox claims require runtime and network decisions beyond default k3s.

NetworkPolicy

Default k3s networking can support normal Kubernetes NetworkPolicy behavior when using compatible networking components; this is enough for standard egress tests [13].

FQDN egress

Cilium FQDN rules are not available unless the cluster uses Cilium CNI. Do not set egressMode: cilium without that platform choice [11][13].

Runtime isolation

gVisor/Kata are not default k3s runtimes. k3s supports alternate containerd runtimes, but they must be installed/configured before runtimeClassName means stronger isolation [14].

Storage

k3s local-path storage exists, but distributed storage may be needed if sandbox state must survive node placement or support multi-node scheduling [15].

Proposed architecture

Keep the first production-facing change inside Paperclip's existing operator boundary; introduce Agent Sandbox only after proving compatibility.

Design principle: prove Paperclip can create, constrain, observe, and clean up Kubernetes execution namespaces before adding a second controller API dependency.

Phased rollout plan

Phase 0 — inventory

Read current Instance.yaml, operator values, namespaces, RBAC, and secret references. Confirm no legacy cloudSandbox path remains.

Phase 1 — job backend smoke

Enable @paperclipai/plugin-kubernetes, set execution mode to kubernetes, choose backend: job, add namespace prefix, quotas, limitranges, standard egress, and conservative resources.

Phase 2 — sandbox-cr trial

Install exact Agent Sandbox release manifests in a non-production overlay or isolated namespace. Confirm CRD API version, RBAC, cleanup, runtimeClass behavior, and logs.

Phase 3 — production promote

Promote only after gates pass: API compatibility, runtime isolation decision, network policy proof, storage decision, rollback tested.

GitOps sequencing

  1. Commit Paperclip Instance change for Phase 1 only.
  2. Run ./flux/scripts/validate.sh.
  3. Push to remote main; watch Flux reconcile Paperclip resources.
  4. Run smoke execution; inspect created namespace/job/RBAC/cleanup.
  5. Only then add Agent Sandbox CRDs/controller as a separate commit.
  6. Install manifest.yaml first; add extensions.yaml only if SandboxTemplate, SandboxClaim, or SandboxWarmPool is required [2][4][5].

Decision gates and validation checklist

API gate

Paperclip sandbox-cr emits Agent Sandbox API version installed in cluster. No v1alpha1/v1beta1 mismatch.

Security gate

RuntimeClass choice documented. Without gVisor/Kata, risk accepted as shared-kernel pod isolation [14].

Network gate

Default deny plus required egress proven. Cilium mode rejected unless Cilium CNI is installed [11][13].

Resource gate

Every sandbox namespace has ResourceQuota and LimitRange. Cleanup removes Jobs, Pods, PVCs, RBAC, and namespaces.

Checklist

  • ./flux/scripts/validate.sh passes locally.
  • Flux Kustomizations reconcile cleanly after push.
  • Paperclip operator logs show plugin load and execution adapter config.
  • Phase 1 job creates under expected namespacePrefix.
  • Job backend cannot escape namespace policy, quotas, or allowed egress.
  • For Phase 2, Agent Sandbox CRDs exist at intended API version before Paperclip references them.
  • Rollback commit returns Paperclip to previous execution config without orphaned namespaces.

Phase 1: Paperclip Kubernetes job backend

apiVersion: paperclip.inc/v1alpha1
kind: Instance
metadata:
  name: paperclip
spec:
  plugins:
    - name: "@paperclipai/plugin-kubernetes"
      version: "0.1.0"
  adapters:
    execution:
      mode: kubernetes
      kubernetes:
        backend: job
        namespacePrefix: paperclip-exec-
        egressMode: standard
        perTenantQuota:
          pods: "10"
          requestsCpu: "2"
          requestsMemory: 4Gi
          limitsCpu: "4"
          limitsMemory: 8Gi
        perTenantLimitRange:
          defaultCpu: "1"
          defaultMemory: 1Gi
          defaultRequestCpu: 250m
          defaultRequestMemory: 512Mi
          maxCpu: "2"
          maxMemory: 2Gi
